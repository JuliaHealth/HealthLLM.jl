Evaluation

The Evaluation module measures whether retrieval grounding improves natural-language → FunSQL generation. Each benchmark task is answered by the same model twice:

  • zero-shot: the question alone, with a system prompt that asks for FunSQL over the OMOP CDM;
  • RAG: the question plus chunks retrieved from the grounding docs, with FUNSQL_SYSTEM_PROMPT.

Each generated query is scored by running it. It must parse, build a FunSQL query, render against the real database schema, execute, and return the same result as the task's gold SQL. String similarity to a reference answer is never used. The two runs are then compared task by task.

Running the benchmark

You need:

  • an OMOP CDM DuckDB file. The benchmark was built on synthea_1M_3YR.duckdb, a Synthea ETL with its tables in schema dbt_synthea_dev;
  • Ollama serving a chat model and nomic-embed-text.
julia --project=scripts/benchmark -e 'using Pkg; Pkg.instantiate()'
julia --project=scripts/benchmark scripts/benchmark/run_benchmark.jl \
    --db synthea_1M_3YR.duckdb --model qwen2.5:7b

On Julia 1.10, also run Pkg.develop(path=".") in that environment, because the [sources] entry pointing at the repository needs Julia 1.11 or later.

The script writes benchmark_results/<timestamp>/results.json, which holds every task's prompt context, generated code, rendered SQL, and outcome. It also writes report.md, a summary you can paste into a write-up. Pass --limit 5 for a quick check, --tiers schema_aware to run one tier, or --modes rag to skip the baseline. The options are listed at the top of the script.

Generated code is evaluated in Julia to build the query, as sanity_check_funsql documents. Run the benchmark only with models you trust, on a machine you don't mind them running code on. The database is attached read-only. The gold SQL's cdm.<table> names are views over it, so no generated query can modify the source file. Every query runs under a timeout, which stops a runaway join over the full patient table.

The task set

data/benchmark/funsql_tasks.jsonl holds 65 tasks curated from the 200-row FunSQL example dataset (FunSQLQueries/train.jsonl) by scripts/benchmark/curate_tasks.jl. A task is kept only if its gold SQL runs on DuckDB and returns at least one row. An empty gold result would be matched by any query that also returns nothing.

DroppedCountWhy
Gold SQL fails on DuckDB114About half call SQL Server functions DuckDB lacks (GETDATE, DATEADD, DATEDIFF(DAY, …), STDEV, DATEFROMPARTS, ISNULL). 28 don't parse in DuckDB, and 9 have an invalid GROUP BY
Gold SQL returns no rows20Concept codes that don't occur in the Synthea data
Gold SQL times out (60 s)1A drug_exposure self-join over 1.1M patients and 98M drug exposures

Each task has a tier, assigned by classify_tier from its gold SQL:

TierTasksNeeds
simple17one table: filter, group, aggregate, order
compositional8joins, subqueries, CTEs, window or set operations
schema_aware40OMOP vocabulary tables (concept, concept_ancestor) to resolve a clinical idea

Only 1 of the 65 dataset FunSQL answers reproduces its gold SQL's result. The rest have bare identifiers (From(drug_era)), lost newlines, or constructs FunSQL doesn't have. Curation keeps a task's FunSQL only when it is verified, so broken references are never retrieved as examples. The RAG mode in this release is therefore grounded on data/grounding/ alone. Repairing the dataset's FunSQL (and porting its SQL Server queries to DuckDB) would grow both the task set and the example pool.

Scoring

Each TaskResult records how far the generated query got:

OutcomeMeaning
correctExecuted and matched the gold result
mismatchExecuted and returned a different result
execute_errorRendered, but the database rejected the SQL
render_errorBuilt, but referenced a table or column the schema lacks
build_errorValid Julia that is not a FunSQL query
parse_errorNot valid Julia (e.g. SQL, or SQL-like pseudocode)
generation_errorThe model call failed
gold_errorThe task's own gold SQL failed. Excluded from all rates

results_match defines "the same result". It compares columns by content rather than alias, ignores row order, and compares numbers with a tolerance. compare_modes pairs the two modes per task and reports the discordant counts with an exact McNemar test, so you can tell a RAG gain from noise.

Leakage

If a task's own reference answer is in the index, retrieving it measures lookup, not grounding. split_tasks holds tasks out with a deterministic, tier-stratified split. Only the other tasks' verified FunSQL is indexed, via examples_document. The default --test-fraction 1.0 evaluates every task and indexes no examples.

Using the harness from Julia

The harness reaches the database, the model, and the retriever only through functions you pass in, so it can be driven from Julia directly or tested offline:

using HealthLLM, FunSQL

tasks = load_tasks(joinpath(pkgdir(HealthLLM), "data", "benchmark", "funsql_tasks.jsonl"))

results = run_benchmark(tasks;
    model     = "qwen2.5:7b",
    executor  = sql -> my_resultset(sql),   # SQL -> ResultSet
    catalog   = my_funsql_catalog,          # FunSQL.SQLCatalog of the database
    retriever = q -> retrieve(store, q, 6)) # question -> hits

summarize(results)[:rag].overall.execution_accuracy
compare_modes(results).p_value
print(markdown_report(results))

scripts/benchmark/omop_duckdb.jl provides open_omop_duckdb and duckdb_executor for DuckDB.
